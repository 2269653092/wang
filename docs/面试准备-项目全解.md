## 一、30 秒 & 3 分钟讲清楚这个项目

### 30 秒版本（电梯演讲）

> 这是一个基于 **LangGraph 多智能体 + RAG** 的瑞士航空客服系统。核心是一个**主管-专家（Supervisor-Specialist）架构**：主助手负责意图识别与任务委派，下设航班、酒店、租车、行程、电商、表单六个专家助手。所有**查询类操作直接执行**，所有**写操作（改签/退票/预订/取消）必须经过人工审批（HITL）**才能落库。知识检索走 Qdrant 向量库，同时用两级 LLM 护栏做越狱检测和相关性过滤。

### 3 分钟版本（展开讲）

| 维度 | 内容 |
|---|---|
| **业务** | 瑞士航空客服：查航班、改签/退票、订酒店、租车、推荐行程、查电商商品与订单、提交联系表单 |
| **架构** | FastAPI + LangGraph 状态图，Supervisor 分派 + 6 个 Specialist 执行 |
| **编排** | LangGraph `StateGraph`，节点=助手/工具，边=条件路由，用 `MemorySaver` 做短期记忆 |
| **检索** | 5 个 Qdrant Collection（faq / flights / hotels / car_rentals / excursions），`text-embedding-3-small`，1536 维，余弦相似度 |

| **存储** | SQLite（业务数据）、Qdrant（向量）、JSON 文件（会话与操作日志） |

### 2.2 State 设计（面试高频：为什么这么设计）

`app/core/state.py`

```python
def update_dialog_stack(left: list[str], right: Optional[str]) -> list[str]:
    """按下或弹出对话框状态堆栈"""
    if right is None:
        return left
    if right == "pop":
        return left[:-1]
    return left + [right]

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    user_info: str
    dialog_state: Annotated[
        list[Literal["assistant", "update_flight", "book_car_rental",
                     "book_hotel", "book_excursion"]],
        update_dialog_stack,
    ]
```

**要点：**

1. **`messages` 用 `add_messages` reducer** —— LangGraph 的核心约定。节点返回值中的 `messages` 会被**追加**而不是覆盖，天然实现多轮对话历史累积。
2. **`dialog_state` 是一个栈**，用自定义 reducer `update_dialog_stack` 实现 push/pop。委派时 `create_entry_node` 返回 `dialog_state: "book_hotel"` 入栈，专家助手完成或 `CompleteOrEscalate` 时出栈。**面试话术：用栈而不是单值，是为了支持嵌套委派（专家 A 内部再转给 B）时能正确回溯。**
3. **`user_info` 无 reducer** —— 直接覆盖语义，每次 `fetch_user_info` 刷新。

> **八股：LangGraph 的 Reducer 是什么？**
> Reducer 定义"节点返回值如何合并进 State"。默认行为是**覆盖**。通过 `Annotated[type, reducer_fn]` 指定自定义合并逻辑。内置的 `add_messages` 支持按消息 id 追加 + 去重 + 支持 `RemoveMessage` 删除。不写 reducer 的字段，后写覆盖先写。

**节点清单：**

| 节点名 | 类型 | 作用 |

**边的三种形态：**

```python

builder.add_edge("fetch_user_info", "guardrail_check")
builder.add_edge("guardrail_check", "primary_assistant")

# 2) 条件边（单函数，返回值即目标节点名）

# 3) 条件边（函数 + 显式映射表，映射表用于类型安全/可读性）
builder.add_conditional_edges(
    "primary_assistant",
    route_primary_assistant,
    {
        "enter_update_flight": "enter_update_flight",
        "enter_woocommerce": "enter_woocommerce",
        ...
        END: END,
    },
)
```

**编译（HITL 关键）：**

```python
memory = MemorySaver()
multi_agentic_graph = builder.compile(
    checkpointer=memory,
    interrupt_before=[
        "update_flight_sensitive_tools",
        "book_car_rental_sensitive_tools",
        "book_hotel_sensitive_tools",
        "book_excursion_sensitive_tools",
    ],
)
```

> **八股：`interrupt_before` vs `interrupt_after`**
> - `interrupt_before`：进入节点**前**暂停。适合"执行前审批"——图停在这里，`snapshot.next` 指向该节点，人看一眼工具参数再决定。
> - `interrupt_after`：节点执行**后**暂停。适合"执行后复核"。
> - 恢复执行：`graph.invoke(None, config)` 从断点继续。
> - 修改状态再继续：`graph.update_state(config, {"messages": [...]})`。

### 2.4 委派机制（Handoff）—— 本项目的精髓

**关键技巧：把 Pydantic 模型当作"伪工具"来做委派。**

```python
# app/assistants/primary_assistant.py
class ToHotelBookingAssistant(BaseModel):
    """转到一名专门助理处理旅馆预订、改建和注销事宜。"""
    location: str = Field(description="...", default="Unknown")
    checkin_date: str = Field(description="...", default="Unknown")
    checkout_date: str = Field(description="...", default="Unknown")
    request: str = Field(description="...")
```

这类模型**没有函数体**，LLM 调用它时不会真的执行代码，而是产生一个带参数的 tool_call，路由函数据此跳转：

```python
def route_primary_assistant(state: State):
    route = tools_condition(state)
    if route == END:
        return END
    tool_calls = state["messages"][-1].tool_calls
    if tool_calls:
        tool_name = tool_calls[0]["name"]
        if tool_name == ToFlightBookingAssistant.__name__:
            return "enter_update_flight"
        elif tool_name == ToHotelBookingAssistant.__name__:
            return "enter_book_hotel"
        ...
        else:
            return "primary_assistant_tools"   # 真工具 → 去 ToolNode
    return "primary_assistant"
```

**为什么这招好（面试加分点）：**

1. **参数即上下文**：委派时 LLM 顺带把 `location`、`checkin_date` 等槽位抽取出来，专家助手一上来就有上下文，不用重新多轮追问。
2. **统一在 tool_calls 里**：委派和真实工具调用走同一套 `tools_condition` 判定，路由逻辑收敛。
3. **零额外协议**：不需要额外的 handoff 框架。

**`enter_xxx` 节点做了什么（`app/utils.py`）：**

```python
def create_entry_node(assistant_name: str, new_dialog_state: str) -> Callable:
    def entry_node(state: State) -> dict:
        last_message = state["messages"][-1]
        tool_messages = []
        if hasattr(last_message, 'tool_calls') and last_message.tool_calls:
            for tool_call in last_message.tool_calls:   # 注意：处理全部 tool_call，不只第一个
                tool_messages.append(ToolMessage(
                    content=(
                        f"The assistant is now the {assistant_name}. Reflect on the above conversation..."
                        "If the user changes their mind ..., call the CompleteOrEscalate function..."
                        "Do not mention who you are—just act as the proxy for the assistant."
                    ),
                    tool_call_id=tool_call["id"],
                ))
        ...
        return {"messages": tool_messages, "dialog_state": new_dialog_state}
    return entry_node
```

> **坑点（面试可以主动讲）：** 每个 tool_call **必须**有对应的 ToolMessage 回应，否则 OpenAI API 报
> `tool_calls must be followed by tool messages`。所以这里遍历所有 `tool_calls` 逐个补 ToolMessage，
> 而不是只补第一个。项目里 `chat_service.py` 甚至专门写了"未回应 tool_call 兜底补 ToolMessage"的补偿逻辑。

路由函数按**工具名集合**分流：

```python
def route_update_flight(state: State):
    route = tools_condition(state)
    if route == END:
        return END
    tool_calls = state["messages"][-1].tool_calls
    safe_toolnames = [t.name for t in update_flight_safe_tools]
    if all(tc["name"] in safe_toolnames for tc in tool_calls):
```

### 2.8 RAG 链路

#### 写入侧（`vectorizer/`）

```
数据源（SQLite 表 / 远程 FAQ md）
   ↓ format_content()：结构化记录 → 自然语言句子
   ↓ 段落切分 → 句子切分 → 单词切分（三级降级，保证 ≤2048 字符）
   ↓ recursive_character_splitting(chunk_size=1800, chunk_overlap=20)
   ↓ aiohttp 异步并发调 /v1/embeddings（批大小 50，批间 sleep 1s）
   ↓ Qdrant upsert（批大小 100）
```

**为什么要 `format_content`？** 因为向量检索是语义匹配，把结构化行转成自然语言句子能显著提升召回质量：

### 2.9 护栏（Guardrails）

`app/guardrails/guardrail_agents.py`：

`app/graph.py` 中的检查节点：

```python
def guardrail_check(state: State, config: RunnableConfig):
    user_messages = [msg for msg in state["messages"] if isinstance(msg, HumanMessage)]
    latest_user_message = user_messages[-1]

    # 1. 越狱检测 → 不通过直接拦截

        f"{jailbreak_guardrail_agent_instructions}\n\nUser Input: {user_input}")
    if not jailbreak_result.is_safe:
        return {"messages": [HumanMessage(content=f"I cannot assist with that request. Reason: ...")]}

    # 2. 相关性检测 → 目前只记日志，仍然放行
    relevance_result = relevance_guardrail_agent.invoke(...)
    if not relevance_result.is_relevant:
        logger.warning(...)   # 拦截代码被注释掉了

    return {"messages": []}   # 放行，不新增消息
```

> **面试会问：为什么用 gpt-4o-mini 而不是主模型？**
> 护栏在**每一次用户输入**都要跑，是高频路径。用小模型 + `temperature=0` 保证：低延迟、低成本、判定稳定。
> 主模型（对话）保留 `temperature=1` 保证回答自然。这是典型的 **成本分层设计**。

## 三、技术栈与对应八股

### 3.1 LangGraph

| 概念 | 本项目用法 | 八股要点 |
|---|---|---|
| `StateGraph` | `builder = StateGraph(State)` | 有状态图编排框架，State 在节点间流动 |
| `State` | `TypedDict` + `Annotated[..., reducer]` | 通常用 TypedDict 或 Pydantic BaseModel |
| Node | 普通函数 `(state, config) -> dict` | 返回的是**状态增量**，不是全量 State |
| Edge | `add_edge` / `add_conditional_edges` | 条件边返回下一个节点名 |
| `START` / `END` | 内置哨兵节点 | `END` 字符串是 `"__end__"` |
| Checkpointer | `MemorySaver()` | 短期记忆；生产用 `SqliteSaver` / `PostgresSaver` |
| `thread_id` | `config = {"configurable": {"thread_id": ...}}` | 区分不同会话，是 checkpoint 的一级 key |
| `interrupt_before/after` | 敏感工具前暂停 | 配合 `invoke(None, config)` 恢复 |
| `get_state` / `update_state` | 查快照 / 改状态 | 时间旅行（time travel）的基础 |
| `ToolNode` | `create_tool_node_with_fallback` | 预置的节点，自动执行 tool_calls |
| `tools_condition` | 路由判定 | 有 tool_calls → `"tools"`，否则 → `END` |
| `with_fallbacks` | 工具报错兜底 | LangChain Runnable 的容错机制 |

**常问八股：**

**Q：LangGraph 和 LangChain 什么关系？**
> LangChain 是"组件库"（模型、提示词、工具、检索器），LangGraph 是"编排框架"，把 LangChain 组件组织成有环图（cyclic graph）。LangChain 的 LCEL 是 DAG（无环），做不了"循环重试""多轮工具调用"，LangGraph 补的就是这个。LangGraph 可以独立使用，不强依赖 LangChain。

**Q：LangGraph 的持久化怎么做？**
> 三层：
> - **Checkpointer**（短期记忆）：每次 super-step 后保存 State 快照，按 `thread_id` 隔离。`MemorySaver`（内存）/ `SqliteSaver` / `PostgresSaver`。
> - **Store**（长期记忆）：跨 thread 的持久化 KV，存用户画像等。
> - **中断恢复**：`interrupt` 后靠 checkpoint 恢复现场。

**Q：State 的 Reducer 默认行为？**
> 默认**覆盖**（last-write-wins）。要追加必须显式指定 Reducer，如 `Annotated[list, add_messages]`。

**Q：子图（Subgraph）怎么用？**
> 把编译好的子图当节点加入父图。适合把每个专家助手封装成独立子图（本项目是平铺的，可以提这个演进方向）。

### 3.2 LangChain Core

| 组件 | 用法 |
|---|---|
| `ChatPromptTemplate.from_messages` | 构建 system + placeholder 多轮提示词 |
| `.partial(time=datetime.now())` | **预绑定**部分变量，避免每轮重算 |
| `("placeholder", "{messages}")` | 消息列表占位符，展开成完整对话历史 |
| `llm.bind_tools([...])` | 把工具 schema 注入模型，开启 function calling |
| `LCEL` 管道 | `prompt | llm.bind_tools(tools)` |
| `@tool` 装饰器 | 函数 → LangChain Tool（自动从 docstring 生成 description） |
| `ToolMessage` / `HumanMessage` / `AIMessage` | 消息类型 |
| `RunnableConfig` | 透传 `configurable`（本项目用来传 `passenger_id`） |
| `RunnableLambda` | 把普通函数包成 Runnable |

**八股：Function Calling 的完整流程？**
> 1. 定义工具（`@tool` + 类型注解 + docstring）
> 2. `llm.bind_tools(tools)` → 把 JSON Schema 塞进请求
> 3. 模型返回 `tool_calls`（不是纯文本）
> 4. 执行工具 → 得到 `ToolMessage`
> 5. 把 ToolMessage 追加回消息列表，再次调用模型
> 6. 模型基于工具结果生成最终回答
>
> **本项目第 4 步由 LangGraph 的 `ToolNode` 自动完成。**

**八股：`@tool` 的 description 从哪来？**
> 优先取函数的 docstring。**所以 docstring 写得好不好直接决定工具召回率** —— 这是项目里工具 docstring 都写得很详细的原因（如 `lookup_policy` 明确写"在进行飞行更改或执行其他 write 事件之前先使用此选项"）。

### 3.3 RAG 全套八股

**Q：RAG 是什么？为什么需要？**
> Retrieval-Augmented Generation：检索 + 生成。解决 LLM 三大问题：**知识过时、幻觉、私有数据不可见**。
> 流程：**Indexing（切分 → 向量化 → 入库）→ Retrieval（查询向量化 → 相似检索）→ Augmentation（拼进 Prompt）→ Generation**。

**Q：Chunk 怎么切？多大合适？**
> 本项目：先按 Markdown 标题（`re.split(r"(?=\n##)", ...)`）语义切分，再段落 → 句子 → 单词三级降级，最后 `RecursiveCharacterTextSplitter(chunk_size=1800, chunk_overlap=20)`。
> 一般经验：中文 300-800 字，英文 500-1000 token，overlap 取 chunk 的 10%-20%。
> **本项目 chunk 偏大（1800）**，因为单条记录内容短、且要控制在 embedding 模型的 2048 字符上限内。

**Q：为什么要 chunk_overlap？**
> 防止语义在切分点被切断。比如一句话横跨两个 chunk，有 overlap 保证至少一个 chunk 包含完整语义。

**Q：向量相似度怎么选？（余弦 / 欧氏 / 内积）**
> - **余弦（Cosine）**：看方向，忽略长度。**文本检索首选**，本项目用 `Distance.COSINE`。
> - **内积（Dot）**：未归一化，受向量模长影响。
> - **欧氏（Euclid）**：看绝对距离。
> 若向量已归一化，余弦与内积等价。

**Q：embedding 维度的坑（本项目真实踩过）**
> `text-embedding-3-small` = 1536 维，而本地 `all-MiniLM-L6-v2` = 384 维。
> **两者不能混用同一个 collection**，否则 Qdrant 报维度不匹配。
> 本项目 `get_embedding_dimensions()` 动态判断，但 `app/vectordb/vectordb.py` 里硬编码了 `size=1536`，切换本地模型时会出问题 —— 这是一个已知缺陷。

**八股：RAG 效果不好怎么优化？（必考题）**

| 环节 | 手段 |
|---|---|
| 索引前 | 优化切分策略、加 metadata（时间/类别/来源）、查询改写前的**假设性问题生成** |
| 检索时 | **混合检索**（向量 + BM25 关键词）、**MMR** 多样性去重、**metadata 过滤**、**多路召回** |
| 检索后 | **Rerank**（用 Cross-Encoder 如 bge-reranker 精排） |
| Query 侧 | **Query Rewriting**（LLM 改写）、**Multi-Query**、**HyDE**（生成假设答案再检索）、**Step-back Prompting** |
| 生成侧 | 引用溯源、拒答阈值、Prompt 压缩 |

> **本项目现状 & 可改进（面试主动说）：** 目前只有**纯向量单路召回，没有 Rerank，没有混合检索**。
> 补 Rerank（bge-reranker-v2-m3）+ BM25 混合召回是最直接的提升点。

### 3.4 Qdrant 向量数据库

**八股：Qdrant 是什么？和其他向量库比？**

| 库 | 特点 |
|---|---|
| **Qdrant** | Rust 写，性能强，支持丰富的 **payload 过滤**，原生支持量化，部署简单 |
| Milvus | 分布式，超大规模（亿级） |
| Weaviate | 自带模块化 ML 模型，GraphQL |
| Chroma | 轻量，嵌入式，适合原型 |
| pgvector | Postgres 扩展，适合已有 PG 栈 |
| FAISS | Meta 的算法库，不是数据库，无持久化/无分布式 |

**八股：ANN 索引算法？**
- **HNSW**（Hierarchical Navigable Small World）：分层可导航小世界图。**Qdrant 默认**。查询快、召回高，但内存占用大、构建慢。
- **IVF / IVF-PQ**：倒排文件索引 + 乘积量化。省内存，适合超大规模，召回略低。
- **LSH**：局部敏感哈希，现已较少用。

> **权衡：HNSW = 用内存换速度；IVF-PQ = 用精度换内存。**

**八股：Qdrant 的 Payload 是什么？**
> 除向量外附带的 JSON 元数据。本项目存了 `content`、`type`、`flight_no`、`departure_airport` 等**原始数据库字段**，
> 使得检索结果可以直接还原成结构化数据（见 `search_flights` 直接从 payload 取字段），不用回查 SQLite。
> **Qdrant 支持在检索时做 payload 过滤**（`Filter` + `FieldCondition` + `MatchValue`），这是它相对 FAISS 的核心优势。

### 3.5 FastAPI / Uvicorn

**八股：FastAPI 为什么快？**
> 1. 基于 **Starlette**（ASGI 框架），原生支持异步
> 2. 基于 **Pydantic** 做序列化/校验，底层是 Rust 写的 `pydantic-core`
> 3. 自动生成 OpenAPI 文档

**八股：ASGI vs WSGI？**
> - **WSGI**（Flask/Django）：同步，一请求一线程，阻塞 IO 会占满线程池。
> - **ASGI**（FastAPI/Starlette）：异步，基于事件循环，IO 等待时让出控制权，单进程可处理大量并发连接。
>
> 本项目：`async def chat(...)` 是协程，内部 `await process_user_message(...)`。

**八股：依赖注入 `Depends`？**
> `Depends(get_session_data)` 在请求处理前执行，返回值注入路由函数参数。
> 本项目用它统一做**会话识别 + Cookie 下发**，避免每个路由重复写。
> 支持嵌套依赖、缓存（`use_cache=True` 默认同请求内复用）。

**八股：uvicorn 是什么？**
> ASGI 服务器。FastAPI 只定义应用，uvicorn 负责跑起来、管理事件循环和连接。
> `--reload` 热重载，`--workers N` 多进程（`gunicorn -k uvicorn.workers.UvicornWorker` 管理）。

### 3.6 Pydantic

**本项目三种用法：**

```python
# 1) 委派工具（无函数体，只做 schema）
class ToBookExcursion(BaseModel):
    location: str = Field(description="The location where the user wants to book a recommended trip.")
    request: str = Field(description="...")

# 2) 结构化输出 schema
class JailbreakOutput(BaseModel):
    is_safe: bool = Field(description="True if the input is safe, False if it's a jailbreak attempt.")
    reasoning: str = Field(description="Brief explanation of the safety decision.")

# 3) HTTP 请求体校验
class ChatMessage(BaseModel):
    message: str
```

**八股：**
- **v1 vs v2**：v2 核心用 Rust 重写，性能提升 5-50 倍。v1 的 `.dict()` / `.parse_obj()` 在 v2 里推荐 `.model_dump()` / `.model_validate()`。
- **`Field(description=...)` 不只是注释** —— 会进 JSON Schema，直接影响 LLM 对工具参数的理解。**这是写好 Agent 的关键细节。**
- **`with_structured_output(Schema)`**：LangChain 把这个 schema 转成模型的 JSON mode / function calling 约束，保证输出可解析。

### 3.7 Python 异步（asyncio）

**本项目用法：**

```python
# vectorizer/vectordb/vectordb.py —— 高并发 embedding 生成
async with aiohttp.ClientSession() as session:
    tasks = [self.process_chunk(chunk, meta, session) for chunk, meta in zip(batch, batch_metadata)]
    for task in tqdm_asyncio.as_completed(tasks, desc="...", total=len(tasks)):
        point = await task
        points.append(point)
    self.client.upsert(collection_name=..., points=points)
```

**八股：asyncio 三件套？**
> **事件循环（Event Loop）** + **协程（Coroutine）** + **Future/Task**。
> 单线程内通过 `await` 在 IO 处主动让出控制权，事件循环调度其他协程。
> 适合 **IO 密集型**（网络请求、文件读写）；**不适合 CPU 密集型**（要用多进程或线程池）。

**八股：`asyncio.gather` vs `as_completed`？**
> - `gather`：并发跑，**按传入顺序**返回结果。
> - `as_completed`：并发跑，**按完成顺序** yield，适合配合进度条（本项目就这么用）。
> 两者默认**不捕获异常**（`return_exceptions=True` 才捕获）。

**八股：GIL 是什么？**
> 全局解释器锁，同一时刻只有一个线程执行 Python 字节码。
> 所以**多线程无法利用多核做 CPU 密集计算**，但**IO 密集场景不受影响**（IO 时释放 GIL）。
> CPU 密集 → `multiprocessing` / `ProcessPoolExecutor`；IO 密集 → `asyncio` / `ThreadPoolExecutor`。

**八股：`async def` 里能不能调阻塞函数？**
> 能，但会阻塞整个事件循环。
> 本项目 `update_ticket_to_new_flight` 是 `async def` 但内部用了**同步的 `sqlite3`** —— 这会阻塞事件循环。
> 正确做法：`await asyncio.to_thread(sync_fn, ...)` 或换 `aiosqlite`。**这是项目的一个真实技术债。**

### 3.8 SQLite

**本项目用法：** 业务数据（航班/机票/酒店/租车/行程），`init_database.sql` 建表建索引。

```sql
CREATE INDEX idx_tickets_passenger_id ON tickets(passenger_id);
CREATE INDEX idx_flights_departure_airport ON flights(departure_airport);
CREATE INDEX idx_hotels_location ON hotels(location);
```

**八股：**
- **SQLite 特点**：零配置、单文件、嵌入式、支持 ACID、并发写用**库级锁**（写会阻塞）。
- **适合**：读多写少、单机、原型、客户端存储。**不适合**：高并发写、分布式。
- **参数化查询防 SQL 注入**：本项目 `cursor.execute("... WHERE ticket_no = ?", (ticket_no,))` —— **面试一定提这个**。
- **事务**：`conn.commit()` 提交，`conn.rollback()` 回滚。本项目改签是两步 UPDATE，应该包在事务里（**现状没有显式事务，是缺陷**）。
- **WAL 模式**：`PRAGMA journal_mode=WAL` 可让读写不互斥。

## 四、实现细节深挖

### 4.1 `Assistant` 类：为什么要用 while 循环？

```python
# app/assistants/assistant_base.py
class Assistant:
    def __init__(self, runnable: Runnable):
        self.runnable = runnable

    def __call__(self, state: State, config: Optional[RunnableConfig] = None):
        while True:
            result = self.runnable.invoke(state, config)
            if not result.tool_calls and (
                not result.content
                or isinstance(result.content, list)
                and not result.content[0].get("text")
            ):
                messages = state["messages"] + [("user", "Respond with a real output.")]
                state = {**state, "messages": messages}
            else:
                break
        return {"messages": result}
```

**面试话术：** 模型有时会返回"空响应"—— 既没有 tool_calls，content 也是空的（或多个 content block 里只有 reasoning 没有 text）。
这在 Agent 里会导致流程卡死（下游拿不到有效消息）。
这里的 `while True` 是一个**自愈重试**：补一条 `"Respond with a real output."` 的用户消息再问一次，直到拿到有效输出。
**注意这里改的是局部 `state` 变量，不是图里的 State** —— 重试只在本次调用内，不会污染对话历史。

### 4.2 工具容错：`create_tool_node_with_fallback`

```python
# app/utils.py
def handle_tool_error(state) -> dict:
    error = state.get("error")
    tool_calls = state["messages"][-1].tool_calls
    return {
        "messages": [
            {"type": "tool", "content": f"Error: {repr(error)}\nPlease fix your mistakes.",
             "tool_call_id": tc["id"]}
            for tc in tool_calls
        ]
    }

def create_tool_node_with_fallback(tools: list):
    return ToolNode(tools).with_fallbacks(
        [RunnableLambda(handle_tool_error)], exception_key="error"
    )
```

**设计亮点（面试加分）：** 工具报错时**不崩溃**，而是把错误文本包装成 ToolMessage 回给 LLM，
让模型**自己看到错误并修正参数重试**（self-correction）。
同时给每个 tool_call 都补了 ToolMessage，避免 `tool_calls must be followed by tool messages` 报错。

### 4.3 数据时间对齐：`update_dates`

```python
# app/utils.py
def update_dates(db_file):
    backup_file = db_file + '.backup'
    if not os.path.exists(backup_file):
        shutil.copy(db_file, backup_file)          # 先备份，只对齐一次

    conn = sqlite3.connect(db_file)
    tables = pd.read_sql("SELECT name FROM sqlite_master WHERE type='table';", conn).name.tolist()
    tdf = {t: pd.read_sql(f"SELECT * from {t}", conn) for t in tables}

    example_time = pd.to_datetime(tdf["flights"]["actual_departure"].replace("\\N", pd.NaT)).max()
    current_time = pd.to_datetime("now").tz_localize(example_time.tz)
    time_diff = current_time - example_time        # 算出数据集时间 vs 现在的时间差

    tdf["bookings"]["book_date"] = pd.to_datetime(...) + time_diff
    for column in ["scheduled_departure", "scheduled_arrival", "actual_departure", "actual_arrival"]:
        tdf["flights"][column] = pd.to_datetime(tdf["flights"][column].replace("\\N", pd.NaT)) + time_diff

    for table_name, df in tdf.items():
        df.to_sql(table_name, conn, if_exists="replace", index=False)
    conn.commit(); conn.close()
```

**为什么需要？** 官方 demo 数据库是固定时间的（比如 2024 年），但 Prompt 里有 `"Current time: {time}"`。
如果数据库时间停在 2024 年，LLM 会认为所有航班都是"过去时"，逻辑就乱了。
所以做一次**时间平移**，把整个数据集"搬"到当下。用 `.backup` 文件保证只做一次（幂等）。

### 4.4 Embedding API 的健壮性设计

```python
async def generate_embedding_async(self, content, session):

                                    timeout=60) as response:
                if response.status != 200:
                    error_text = await response.text()
                    raise Exception(f"HTTP {response.status}: {error_text}")
                result = await response.json()
                if "data" in result and len(result["data"]) > 0:
                    return result["data"][0]["embedding"]
                raise ValueError(f"Unexpected API response: {result}")
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            delay = base_delay * (2 ** attempt)     # 指数退避：1, 2, 4, 8 秒
            await asyncio.sleep(delay)
```

**面试话术（可展开）：**
- **指数退避（Exponential Backoff）**：避免瞬时故障打垮服务，也避免重试风暴。生产上还会加**抖动（jitter）**防止重试同步。
- **模型自动探测**：`test_openai_connection()` 先拉 `/v1/models`，再依次探测 9 个候选模型名，把第一个可用的存进 `self.working_model`。**为了兼容 api2d 这类 OpenAI 中转商**。
- **批控速**：批大小 50，批间 `sleep(1)`，防速率限制（rate limit）。

#### ① langgraph

```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.prebuilt import ToolNode, tools_condition

# 1. 定义 State
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]

# 2. 建图
builder = StateGraph(State)
builder.add_node("agent", agent_fn)                     # 加节点
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "agent")                        # 普通边
builder.add_conditional_edges("agent", route_fn)        # 条件边
builder.add_conditional_edges("agent", route_fn,        # 条件边 + 显式映射
                              {"tools": "tools", END: END})

# 3. 编译（带记忆 + 中断）
graph = builder.compile(checkpointer=MemorySaver(),
                        interrupt_before=["tools"])

# 4. 运行
config = {"configurable": {"thread_id": "user-123"}}
for event in graph.stream({"messages": [("user", "hi")]}, config, stream_mode="values"):
    print(event["messages"][-1].content)

# 5. 查状态 / 改状态 / 恢复
snapshot = graph.get_state(config)          # 快照，snapshot.next 是下一批要跑的节点
graph.update_state(config, {"messages": [ToolMessage(...)]})
graph.invoke(None, config)                  # 从断点继续
```

**流式模式：**
- `stream_mode="values"`：每个节点后输出**完整 State**
- `stream_mode="updates"`：只输出**增量**
- `stream_mode="messages"`：按 token 流式（配合 LLM 流式输出）

## 六、面试高频追问 Q&A

### Q1：为什么用多智能体，一个 Agent 全做完不行吗？

> **不行，主要有三个问题：**
> 1. **工具太多导致选择困难**：本项目总共 20+ 个工具，全塞给一个 Agent，模型选错工具的概率显著上升，且 prompt 会很长。
> 2. **权限控制**：只有专家助手才有写权限。单个 Agent 无法在架构层面强制"必须先委派才能改数据"。
> 3. **上下文污染**：改签对话和查商品对话的上下文不该混在一起。专家助手各自有独立 prompt 和工具集，上下文更聚焦。
>
> **代价**：多一次 LLM 调用（委派决策），延迟和成本上升。所以本项目里纯查询（查航班）主管自己就做了，不委派。

### Q2：主助手怎么决定委派给谁？

> 靠 **prompt 里的委派规则 + 工具的 description**。
> prompt 里明确写了 `"DELEGATION RULES (ALWAYS delegate, never try to handle these yourself)"` 并逐条列举映射关系；
> 每个委派工具（`ToHotelBookingAssistant` 等）的 docstring 和 `Field(description=...)` 描述了自己的适用场景和参数。
> 模型输出 tool_call → 路由函数按名字跳转。

### Q3：如果用户一句话里要办两件事（比如"查一下我的车和酒店"）怎么办？

> 本项目在 prompt 里**显式禁止多委派**：
> `"If the user asks about MULTIPLE services in one query, do NOT delegate to multiple assistants"`，
> 要求主管自己用 `search_flights` 查一下，给个摘要，然后**反问用户要先办哪个**。
> 这是工程上的务实选择 —— 串行委派会导致状态栈混乱。

### Q4：为什么敏感操作要人工审批？技术上怎么保证不会被绕过？

> **业务上**：改签/退票/取消是有经济后果的不可逆操作，LLM 幻觉或误解用户意图会造成真实损失。
>
> **技术上三重保障：**
> 1. **架构层**：写工具被放进 `xxx_sensitive_tools` 节点，编译图时 `interrupt_before`，物理上到这个节点就停。
> 2. **工具层**：`gohumanloop` 的 `@require_approval(execute_on_reject=False)` 装饰器，函数执行前再拦一道。
> 3. **数据层**：工具内部还做了归属校验：
> ```python
> cursor.execute("SELECT * FROM tickets WHERE ticket_no = ? AND passenger_id = ?",
>                (ticket_no, passenger_id))
> ticket = cursor.fetchone()
> if not ticket:
>     return f"Ticket {ticket_no} not found for passenger {passenger_id}."
> ```
> 即使前两层都被绕过，也改不了别人的票。

### Q5：拒绝之后流程怎么走？

> 不是简单报错，而是**把拒绝理由作为 ToolMessage 回写给 LLM**，让它自己向用户解释并继续服务：
> ```python
> ToolMessage(
>     tool_call_id=tool_call_id,
>     content=f"API call denied by user. Reasoning: '{user_input}'. Continue assisting, accounting for the user's input.",
> )
> ```
> 这样用户说"我要改到明天而不是后天"，LLM 能理解并重新发起正确请求。**这是 HITL 做得好不好的关键分水岭。**

### Q6：多轮对话记忆怎么做的？重启后还在吗？

> 用 LangGraph 的 `MemorySaver` Checkpointer，按 `thread_id` 隔离。Web 场景下 `thread_id` = Cookie 里的 `session_id`。
> **不在** —— `MemorySaver` 是纯内存的，进程重启全丢。生产要换 `SqliteSaver` / `PostgresSaver`，
> 或者用 Redis 做分布式 checkpoint。**这是明确的待改进项。**

### Q7：向量检索和 SQL 查询怎么分工？

> - **向量检索（Qdrant）**：处理**模糊的自然语言查询**。如"下周去上海的航班" —— 语义匹配，返回相似航班。
> - **SQL（SQLite）**：处理**精确的、带约束的查询和写操作**。如"票号 X 属于乘客 Y 吗"、"把票改成航班 Z"。
>
> **组合拳**：先用向量做召回（找到候选航班 ID），再用 ID 去 SQL 做精确操作和事务。
> 这也是为什么 payload 里存了完整的原始字段 —— 检索结果可以直接用，不必二次回查。

### Q8：为什么要做两级护栏？只用一级不行吗？

> 两个护栏关注的维度不同：
> - **越狱检测**：安全维度，防 prompt injection、SQL 注入话术、套取系统提示词。**命中即拦截**。
> - **相关性检测**：业务边界维度，判断问题是否在本系统服务范围内。
>
> 目前实现上**只有越狱会真正拦截**，相关性命中只记 warning 日志、仍然放行 ——
> 这是有意的保守设计（避免误杀），但也可以说是不够彻底。

### Q9：LLM 输出不稳定怎么办？

> 本项目的应对：
> 1. **护栏和决策用 `temperature=0`**（确定性），**对话用 `temperature=1`**（自然）。
> 2. **结构化输出** `with_structured_output(Pydantic Schema)`，保证字段一定存在、类型一定对。
> 3. **`Assistant` 类的 while 重试**，处理空输出。
> 4. **工具报错兜底** `with_fallbacks`，把错误回喂给模型自纠。
> 5. **Prompt 里明确约束**：`"When searching, be persistent. Expand your query bounds if the first search returns no results."`

### Q10：成本怎么控制？

> 1. **模型分层**：护栏用 `gpt-4o-mini`，主对话用配置化模型（`.env` 里 `OPENAI_MODEL`）。
> 2. **`max_tokens` 限制**（默认 1000），从 `settings.MAX_TOKENS` 读。
> 3. **检索条数限制** `limit=2`，减少 prompt 长度。
> 4. **敏感操作人工确认**，避免反复的无效调用。
> 5. **向量化批控速**（批 50、间隔 1s），减少重试和限流。

## 八、八股速记清单

### Python 基础

- **GIL**：全局解释器锁，同时刻仅一线程执行字节码；IO 密集不受影响，CPU 密集用多进程。
- **深拷贝 vs 浅拷贝**：`copy.copy` 只拷一层，`copy.deepcopy` 递归。
- **`*args` / `**kwargs`**：位置变参 / 关键字变参。本项目 `def search_faq(query: str, limit: int = 2)` 用 `*`（如 `fetch_user_flight_information(*, config)`）强制关键字参数。
- **装饰器**：`@tool` 在 `@humanloop_adapter.require_approval(...)` 之上，执行顺序是**从下往上**装饰、`@tool` 最后生效。
- **生成器 vs 列表**：`chunked()` 是惰性的，省内存。
- **`with` 语句**：上下文管理器，`__enter__` / `__exit__`。本项目大量用于数据库连接、`httpx.Client`。
- **`if __name__ == "__main__"`**：模块直接运行时才执行。

### 并发

- **协程 vs 线程 vs 进程**：协程（用户态、单线程、IO 密集）＜ 线程（内核态、受 GIL）＜ 进程（多核、开销大）。
- **`asyncio.run()`** vs **`loop.run_until_complete()`**。
- **`await` 只能在 `async def` 里用**。
- **信号量限流**：`asyncio.Semaphore(n)`（本项目没用，但常问，可提"如果要限制并发 embedding 请求数可以加"）。

### LLM / Agent

- **ReAct**：Reasoning + Acting 交替（Thought → Action → Observation）。
- **Function Calling / Tool Use**：见上文 3.2。
- **Multi-Agent 架构模式**：Supervisor（本项目）、Swarm（对等移交）、Hierarchical（多层）、Network。
- **Agent 记忆**：短期（checkpoint/thread）、长期（store）、情景（few-shot）、语义（RAG）。
- **幻觉成因与缓解**：RAG、引用溯源、降低 temperature、拒答机制、事实一致性校验。
- **Prompt 工程技巧**：角色设定、few-shot、CoT、明确约束、分隔符（本项目用 `<Flights>...</Flights>` XML 标签）。

### 数据库

- **索引原理**：B+ 树（关系库）、HNSW（向量库）。
- **最左前缀原则**。
- **事务 ACID**：原子性、一致性、隔离性、持久性。
- **隔离级别**：读未提交 / 读已提交 / 可重复读 / 串行化（MySQL 默认可重复读）。
- **SQL 注入与防范**：参数化查询（本项目用了 `?` 占位符）。

### 系统设计

- **怎么设计高并发客服系统？**
  > 接入层（负载均衡）→ 网关（限流/鉴权）→ 会话服务（Redis 存会话）→ Agent 编排层（LangGraph，异步 + 队列削峰）→ 模型网关（多模型路由/降级/缓存）→ 数据层（业务库 + 向量库）。
  > 关键：**LLM 调用异步化 + 流式输出 + 结果缓存 + 幂等（同一 request_id 去重）**。
- **怎么保证幂等？** request_id 去重、数据库唯一索引、upsert 而非 insert（本项目 Qdrant 就用 `upsert`）。
- **怎么观测？** 日志（本项目 `operation_log`）、链路追踪（LangSmith / OpenTelemetry）、Token 与成本监控。
